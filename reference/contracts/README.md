# Proof of One — reference smart contracts

> **Reference code for review and testing only. Not audited. The verifier is generated from a TEST-ONLY trusted setup — do not deploy.**

Reference implementation of the on-chain part of [`docs/specs/contracts-v0.1.md`](../../docs/specs/contracts-v0.1.md):

| Contract | Role |
|---|---|
| `IdentityRegistry` (`Registries.sol`) | Accepts identity leaves with a valid unlinkable-registration proof π_reg from [`../enrolment-circuit`](../enrolment-circuit/); each credential can be used once; leaves enter a depth-32 Poseidon tree only in full batches, each inserted with a batch insertion proof π_batch checked against the chain hash recorded at registration |
| `RevocationRegistry` (`Registries.sol`) | Indexed Merkle tree of revoked handles; each update by the enclave operator carries a revocation proof π_revoke; every revocation public with a reason code |
| `ProofOfOnePolls` | Polls, ballots and results for 4 options. Membership snapshots are read from the two registries. A ballot needs a valid proof from [`../ballot-circuit`](../ballot-circuit/); a result must pass the checks the contract can make on its own |
| `Groth16Verifier`, `RegistrationVerifier`, `BatchInsertVerifier`, `RevokeVerifier` | Generated by snarkjs from the TEST-ONLY setups |
| `BabyJubjub` | Curve and subgroup check for the tally key |

Poseidon is deployed from the bytecode generated by circomlibjs, so the on-chain hash is the one used in the circuits.

## What the contract enforces

| Rule | Where |
|---|---|
| A registration needs a valid π_reg under the published enclave key-set root; a credential can be used only once | `IdentityRegistry.register` |
| Leaves are inserted only in full batches, with a proof that matches the registered leaves and order | `IdentityRegistry.insertBatch` |
| A revocation needs a proof that the handle fits a gap in the sorted list and is appended at the next free slot | `RevocationRegistry.revoke` |
| Poll snapshots (identity root, revocation root, eligible count) come from the registries, not the creator | `createPoll` |
| The tally key is on Baby Jubjub and in the prime-order subgroup (checked once per poll) | `createPoll` → `BabyJubjub.isInSubgroup` |
| Polls are open for at least 48 hours (room for forced inclusion) | `createPoll` |
| Every ballot carries a valid π_vote proof | `vote` |
| Public inputs are rebuilt from the poll's own parameters, never taken from the caller | `vote` |
| Proofs are bound to this chain, this contract and this poll (`contextHash`) | `vote` |
| Latest ballot per nullifier, re-vote cap, count of distinct voters, ordered ballot chain | `vote` |
| No ballots outside the open period | `vote` |
| A result must match the ballot chain | `publish` |
| Totals must equal the number of distinct voters (one-hot ballots) | `publish` |
| Voters must not exceed eligible identities | `publish` |
| A 7-day challenge period applies before a result becomes final | `finalize` |
| Anyone may mark a result "withheld" if it is not published within 14 days | `markWithheld` |

Ballot ciphertexts are **not** checked for subgroup membership on-chain. The proof computes them from Base8 and the already-validated tally key, so they are in the subgroup by construction. This saves a large amount of gas per ballot.

## Not yet implemented

- An enclave signature on revocations. Here a trusted operator address is used.
- Trustee signatures on the tally key and on results. In this reference, the poll creator publishes the result.
- On-chain challenges (DLEQ failure, aggregate mismatch). These are checked off-chain by the recount tool in [`../tally`](../tally/).
- Relay (ERC-4337), breakdown cells, ballot aggregation, governance.

## Run it

```bash
# requires ../tally, ../ballot-circuit and ../enrolment-circuit installed and built (see their READMEs)
npm install
npm test        # compiles with solc-js, then runs end-to-end tests on an in-process EVM
```

## Tests

The tests run on ganache, an in-process EVM. They use **real** Groth16 proofs for both registration and ballots. The phone's view of the registries is rebuilt from contract events only.

| Test | Expected result |
|---|---|
| Registration with π_reg; batch insertion with π_batch | Accepted; reused credential rejected; incomplete batch refused; insertion proof with a wrong root rejected |
| Phone's trees rebuilt from events | Same roots as on-chain |
| Poll creation | Bad tally key and short polls rejected; snapshot and eligible count taken from the registries |
| Ballots and a re-vote | Accepted; the later ballot replaces the earlier one |
| Forged or replayed ballots | Proof attached to other ciphertexts, or replayed in another poll: rejected |
| Re-enrolment | Old identity revoked on-chain with π_revoke (a proof for a wrong root is rejected); in later polls the old identity cannot vote, while the new one and others can |
| Ballot chain | Identical to the chain rebuilt by the reference tally from events |
| Tally and result | Correct totals; wrong totals or chain rejected; challenge period; finalize; unpublished poll marked withheld |

## Measured gas (reference, unoptimised)

| Operation | Gas | Spec estimate |
|---|---|---|
| `register` (π_reg verification, storage, chain hash) | 334,589 | about 300,000 |
| `insertBatch`, 4 leaves, with π_batch | **293,548** (was 4,205,814 with on-chain hashing) | about 400,000 per batch |
| `revoke`, with π_revoke | **294,646** (was 4,027,982 with on-chain hashing) | — |
| `createPoll` (including subgroup check of the tally key) | 629,485 | — |
| `vote`, first ballot | 533,603 | about 420,000 |
| `vote`, re-vote | 442,985 | about 400,000 |
| `publish` | 158,118 | about 300,000 |

The cost of `insertBatch` does not grow with the batch size: with a realistic batch of 1,024 leaves it is under 300 gas per leaf. Each registration pays about 32,000 gas more for the chain hash. Revocation uses the same approach.
