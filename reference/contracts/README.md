# Proof of One — reference smart contracts

> **Reference code for review and testing only. Not audited. The verifier is generated from a TEST-ONLY trusted setup — do not deploy.**

Reference implementation of the on-chain part of [`docs/specs/contracts-v0.1.md`](../../docs/specs/contracts-v0.1.md):

| Contract | Role |
|---|---|
| `IdentityRegistry` (`Registries.sol`) | Accepts identity leaves with a valid unlinkable-registration proof π_reg from [`../enrolment-circuit`](../enrolment-circuit/); each credential can be used once; leaves enter a depth-32 Poseidon tree only in full batches, each inserted with a batch insertion proof π_batch checked against the chain hash recorded at registration |
| `RevocationRegistry` (`Registries.sol`) | Indexed Merkle tree of revoked handles; each update by the enclave operator carries a revocation proof π_revoke; every revocation public with a reason code |
| `ProofOfOnePolls` | Polls, ballots and results for 4 options. Membership snapshots are read from the two registries. A ballot needs a valid proof from [`../ballot-circuit`](../ballot-circuit/), sent alone (`vote`) or in a batch (`voteBatch`); the contract keeps the encrypted totals itself; a result is accepted only with a tally proof π_tally checked against them, and is final at once ([design](../../docs/specs/on-chain-tally-verification-v0.1.md)) |
| `BallotBatchVerifier` | Checks many ballot proofs of one poll together with n + 3 pairings; generated from the ballot verification key by `scripts/gen-batch-verifier.js` with this project's own template ([design](../../docs/specs/ballot-aggregation-v0.1.md)) |
| `Groth16Verifier`, `RegistrationVerifier`, `BatchInsertVerifier`, `RevokeVerifier` | Generated by snarkjs from the TEST-ONLY setups |
| `BabyJubjub` | Curve and subgroup checks; point addition for the running sum |

Poseidon is deployed from the bytecode generated by circomlibjs, so the on-chain hash is the one used in the circuits.

## What the contract enforces

| Rule | Where |
|---|---|
| A registration needs a valid π_reg under the published enclave key-set root; a credential can be used only once | `IdentityRegistry.register` |
| Leaves are inserted only in full batches, with a proof that matches the registered leaves and order | `IdentityRegistry.insertBatch` |
| A revocation needs a proof that the handle fits a gap in the sorted list and is appended at the next free slot | `RevocationRegistry.revoke` |
| Poll snapshots (identity root, revocation root, eligible count) come from the registries, not the creator | `createPoll` |
| The tally key is on Baby Jubjub and in the prime-order subgroup (checked once per poll) | `createPoll` → `BabyJubjub.isInSubgroup` |
| Polls are open for at least 48 hours (room for forced inclusion) | `createPoll` |
| Every ballot carries a valid π_vote proof, checked alone or in a batch | `vote`, `voteBatch` |
| A **recovery ballot** (π_recover, [ballot-circuit](../ballot-circuit/)) replaces the old identity's ballot when the caller holds the new identity linked to it, current and not revoked; the identity root is the registry's current one. Afterwards ordinary ballots under that nullifier are refused, and recovery ballots get one ballot beyond the re-vote cap (Decision Log #52, point 2) | `recoveryVote` |
| A ballot proves non-revocation against the **current** revocation root, not the one at poll creation, so an identity revoked while a poll is open cannot vote in it any more (Decision Log #52). A proof against the root before the latest revocation is accepted for 10 minutes after it, so ballots being sent at that moment are not lost. The contract computes the poll's `pollHash` once per root it meets | `vote`, `voteBatch` |
| Public inputs are rebuilt from the poll's own parameters, never taken from the caller: the poll's `pollHash`, computed once at creation, binds roots, poll id, tally key, policy and context | `createPoll`, `vote` |
| Proofs are bound to this chain, this contract and this poll (`contextHash`) | `vote` |
| Latest ballot per nullifier, re-vote cap, count of distinct voters, ordered ballot chain; a batch is recorded exactly as if sent ballot by ballot | `vote`, `voteBatch` |
| A batch lists its nullifiers in strictly increasing order, so no nullifier appears twice and a relay cannot choose which of a member's answers counts | `voteBatch` |
| No ballots outside the open period | `vote` |
| In a sampled poll, the seed comes from a block created after the membership snapshot, and only invited members can vote: the top 64 bits of Poseidon(13, nf, seed) must be below the poll's threshold | `fixSeed`, `invited`, `vote`, `voteBatch` |
| A result must match the ballot chain | `publish` |
| Totals must equal the number of distinct voters (one-hot ballots) | `publish` |
| Voters must not exceed eligible identities | `publish` |
| The contract keeps the homomorphic sum of the counted ballots; a re-vote must hand over the ballot it replaces, which is checked against its stored hash and subtracted | `vote`, `voteBatch` |
| A result is accepted only with a tally proof π_tally ([tally-circuit](../tally-circuit/)) that every trustee's DLEQ proof is valid, that their Lagrange combination gives the published D_j, and that B_j − D_j = count_j·G against the contract's own sum; the contract builds the public inputs itself | `publish` |
| Exactly t = 3 trustees, distinct and in increasing order, with keys matching the commitment made at poll creation | `createPoll`, `publish` |
| A result that passes is final at once; there is no challenge period (Decision Log #53) | `publish` |
| Anyone may mark a result "withheld" if no valid result is published within 14 days | `markWithheld` |

Ballot ciphertexts are **not** checked for subgroup membership on-chain. The proof computes them from Base8 and the already-validated tally key, so they are in the subgroup by construction. This saves a large amount of gas per ballot.

## Not yet implemented

- An enclave signature on revocations. Here a trusted operator address is used.
- Trustee signatures on the tally key and on results. In this reference, anyone may publish a result; only a correct one can pass.
- Tally circuits for thresholds other than 3.
- The contracts deployed on the test network (deployment 2) predate `recoveryVote`; the constructor now also takes the recovery verifier, so recovery ballots arrive with the next deployment.
- Relay (ERC-4337), breakdown cells, recursive ballot aggregation, governance. Batched verification (`voteBatch`) is implemented.

```bash
# requires ../tally, ../ballot-circuit, ../enrolment-circuit and ../tally-circuit (with its test key) installed and built (see their READMEs)

npm test        # compiles with solc-js, then runs end-to-end tests on an in-process EVM
# the recovery test needs ../ballot-circuit/setup/recovery_test.zkey: run `npm run build:recovery && npm run setup:recovery` there
```

## Tests

The tests run on ganache, an in-process EVM. They use **real** Groth16 proofs for both registration and ballots. The phone's view of the registries is rebuilt from contract events only.

| Test | Expected result |
|---|---|
| Registration with π_reg; batch insertion with π_batch | Accepted; reused credential rejected; incomplete batch refused; insertion proof with a wrong root rejected |
| Phone's trees rebuilt from events | Same roots as on-chain |
| Poll creation | Bad tally key, short polls, trustee keys that are invalid or do not fit the tally key, and a bad threshold rejected; snapshot and eligible count taken from the registries |
| Ballots and a re-vote | Accepted; the later ballot replaces the earlier one |
| Forged or replayed ballots | Proof attached to other ciphertexts, or replayed in another poll: rejected |
| Re-enrolment | Old identity revoked on-chain with π_revoke (a proof for a wrong root is rejected). In the poll already open: another member's ballot proven against the previous root is accepted within 10 minutes; the revoked identity's ballot proven against that root is refused after them, and no ballot can be proven for it against the new root. In later polls the old identity cannot vote, while the new one and others can |
| Recovery ballot | After Alice's re-enrolment, her new identity carries a handle linked to the old one. A recovery ballot proven for other ciphertexts or another nullifier is refused, and so is one that names the wrong replaced ballot; the correct one replaces the old identity's ballot (the count of voters stays the same), sets `recovered` and is reflected in the final, proved result. The new identity cannot vote in the poll directly (not in its snapshot). Not yet tested on-chain: an ordinary ballot refused after a recovery (`Recovered`), which needs a valid ballot within the revocation grace |
| Batched ballots | Batches of 1, 2, 4 and 7 accepted; a re-vote without the replaced ballot, or with another one, refused; a swapped ciphertext, reordered proofs, a proof for another poll or an invalid point rejects the whole batch; the same nullifier twice in one batch, or nullifiers out of order, refused (re-votes go in separate transactions); chain and decrypted totals identical to single submission; the contract's running sum equals the reference tally's |
| Sampled poll | No ballot before the seed is fixed; the seed cannot be fixed early or twice; the contract's invitation check agrees with the phone's for every member; invited members vote alone and in a batch; a member who was not invited is refused, alone or in a batch |
| Ballot chain | Identical to the chain rebuilt by the reference tally from events |
| Tally and result | Correct totals; wrong totals, wrong chain, wrong trustee keys, too few, unordered or unknown trustees rejected by the contract's own checks |
| Tally proof | A publisher who forges one trustee's partial decryption so that forged counts still combine cannot make a tally proof for it; forged counts with a matching D, the right counts with another trustee set than the one proved, or an altered proof are refused. The correct result is accepted and final at once, and cannot be replaced. In a poll without ballots, honest partial decryptions (all identity points) are proved and accepted |
| Withheld | Unpublished poll marked withheld |

## Measured gas (reference, unoptimised)

| Operation | Gas | Spec estimate |
|---|---|---|
| `register` (π_reg verification, storage, chain hash) | 334,601 | about 300,000 |
| `insertBatch`, 4 leaves, with π_batch | **293,548** (was 4,205,814 with on-chain hashing) | about 400,000 per batch |
| `revoke`, with π_revoke | **294,646** (was 4,027,982 with on-chain hashing) | — |
| `createPoll` (subgroup checks of the tally key and 5 trustee keys, key consistency, `pollHash`, the 16 slots of the running sum) | 3,640,236 (921,874 before the tally checks) | — |
| `vote`, a voter's first ballot | **522,580** (514,047 before revocations reached open polls; 392,084 before the running sum) | about 420,000 |
| `vote`, re-vote | **528,789** (520,183 before revocations reached open polls; 374,839 before the running sum) | about 400,000 |
| `voteBatch`, n ballots | **about 440,000 + 124,000 · n** (measured for n = 1, 2, 4, 7; was 349,000 + 101,000 · n) | — |
| `vote`, first ballot of a poll after a revocation, proven against the previous root (computes the new `pollHash` and verifies twice) | 1,018,969 | — |
| `recoveryVote` (π_recover verification, replaces the old identity's ballot) | 568,963 | — |
| `publish`, with the tally proof π_tally (t = 3, 4 options) | 853,274 (227,095 with challenges; 158,145 before) | — |
| `fixSeed` (sampled polls, once per poll) | 50,587 | — |
| Invitation check in a sampled poll | about 50,000 more per ballot | — |

Keeping the encrypted totals on-chain costs about 23,000 gas more per ballot in a batch (about 131,000 instead of 106,000 per ballot in a batch of 64), and removes the need to trust anyone's addition. Before this, two earlier changes had brought a ballot down to what the spec estimated: the nine per-poll values are bound by one `pollHash` instead of nine public inputs, and storage is packed (latest ballot and counter in one slot; both poll counters in one slot). Ballot aggregation is the next large reduction.

The cost of `insertBatch` does not grow with the batch size: with a realistic batch of 1,024 leaves it is under 300 gas per leaf. Each registration pays about 32,000 gas more for the chain hash. Revocation uses the same approach.
